# Review: ARCHITECTURE-SPINE.md (Ameland Vriendenweekend PWA)

**Reviewer stance:** independent, fresh-eyes, checked against `BUILD_BRIEF.md`, `Main.dc.html`, `Admin.dc.html`.

## Verdict

The spine is well-scoped and mostly self-consistent, correctly identifies the mockup's real gaps (gating, admin auth, push coupling, content-config shape) and fixes them with enforceable rules, but it leaves the site's core secrecy mechanism structurally unresolved against its own "static-first" claim and is silent on several small-but-real operational dimensions (passcode rate-limiting, error/observability contract, backup posture), so it needs one more pass before it's safe to build from.

## Findings

1. **[HIGH] Static-first paradigm is not reconciled with the gating check, leaving the site's core secrecy mechanism unresolved.** The Design Paradigm states pages are "static, prerendered" with "almost nothing... server-computed at request time," and AD-7 says all chapter content (title, description, SVG refs) is static authored content baked in at build time. AD-2 then requires the public page to "check `trip.chapters[id].unlocked`... before rendering its real content." Read together, this only works if the real (locked) content ships in the static bundle to every visitor and is merely hidden client-side pending an API check — which means a visitor can view-source or inspect the JS bundle/network payload and see next chapter's content before the organizer unlocks it. That directly undermines the premise the whole site is built around (a paced surprise reveal) and is exactly the kind of ambiguity AD-2 says it wants to prevent ("two builders inventing incompatible gating"): one builder could ship all content to the client and hide it with CSS (spoilable), another could try to keep pages "static" but redact locked-chapter fields server-side per request (which contradicts "nothing computed at request time" and turns pages effectively dynamic). The spine picks neither option.
   **Fix:** Add an explicit sub-rule to AD-2 (or a new AD) stating one of: (a) locked-chapter content fields are deliberately shipped to the client and hidding is presentation-only — i.e., secrecy is "soft," acceptable because the audience is trusted friends, not an adversary; or (b) the trip-state API response itself omits/redacts locked chapters' real content fields (title/description/SVG) and only returns the placeholder + `unlocked:false`, with the static build only ever containing the placeholder markup, real content fetched and swapped in only once unlocked. Option (b) is the one consistent with "secrecy premise" language in AD-3; make it explicit.

2. **[HIGH] No rate-limiting / brute-force protection for the shared admin passcode.** AD-5 defines a single shared passcode as the entire auth boundary for the admin route, with no accounts, no MFA, no lockout. There is no AD, Consistency Convention, or Deferred entry addressing throttling or rate-limiting of passcode attempts. Since the passcode is the *only* thing standing between a public visitor and the ability to trigger `AD-3`'s protected write path (chapter unlock + push fanout to everyone), an unthrottled login endpoint is brute-forceable, especially since the admin route's existence and URL are not secret (BUILD_BRIEF explicitly notes `Admin.dc.html` is "reachable by anyone who knows the URL").
   **Fix:** Add a rule to AD-5 (or a new AD) requiring basic throttling on the passcode-check route — e.g., a fixed delay/backoff or a per-IP attempt counter (Vercel KV, Upstash, or even an in-memory/edge-config counter given the low traffic), with a stated lockout or increasing-delay behavior. Even a minimal rule ("max 5 attempts per 15 minutes per IP, else 429") closes the gap.

3. **[MEDIUM] Consistency Conventions table promises "error shapes, envelopes" but never defines them.** The table's "Data & formats" row lists its scope as "(ids, dates, error shapes, envelopes)" but the convention text only covers dates and the `slug` routing key — no error response shape or success/error envelope convention is given anywhere in the document, despite four separate API routes (`trip/[slug]`, `admin/toggle`, `push/subscribe`, `packing/check`) that will each need to signal success/failure to client-side islands. This is an internal inconsistency (a column header commits to a topic the content doesn't cover) and a real gap — without a shared envelope, one route might return `{error: "..."}` and another a bare 500 with no body, and client islands will diverge in how they handle failures.
   **Fix:** Either trim the row's stated scope to match what's actually decided, or add one line specifying a shared JSON error shape (e.g., `{ ok: false, error: string }` on failure, `{ ok: true, data }` on success) that all four API routes must use.

4. **[MEDIUM] AD-3's "no mutation" wording is ambiguous against AD-6 and the public push-subscribe route.** AD-3 says "the public page and its trip-state API are read-only, unauthenticated, and expose no mutation," while AD-6 and the Structural Seed both establish that `packing/check.ts` (writes shared checked-state) and `push/subscribe.ts` (writes a subscription row) are public, unauthenticated, and mutating. Read narrowly, "the public page and its trip-state API" is meant to refer only to the page itself plus the `GET trip/[slug]` route — but "Binds: all write paths" at the top of AD-3, combined with the categorical "expose no mutation," invites a builder to misread this as forbidding all public-initiated writes, which would contradict AD-6 outright.
   **Fix:** Reword AD-3's rule to explicitly carve out the exception, e.g.: "...The public page and its read-only trip-state API (`GET /api/trip/[slug]`) expose no mutation. The narrow-purpose public write routes (`push/subscribe`, `packing/check`) are intentional exceptions scoped to AD-4 and AD-6 respectively, and write nothing outside those specific fields."

5. **[MEDIUM] Push subscriptions aren't scoped to a trip in the data model, despite "reusable template for future trips" being the architecture's headline scope claim.** AD-7's schema and the Structural Seed's `push/subscribe.ts` ("store a push subscription") don't state whether a subscription record is keyed to a trip `slug`. If the same site/PWA install is reused for a future trip (the explicit stated goal in `scope:` and AD-7's "Prevents" clause), it's unclear whether old subscribers from Trip A automatically get Trip B's unlock notifications (possibly desired, possibly not) or whether that's even structurally possible without a `slug` foreign key on the subscription row.
   **Fix:** Add a `tripSlug` (or equivalent) field to the push-subscription shape in AD-7, and one sentence stating the intended behavior for repeat use across trips (e.g., "subscriptions are per-trip; a new trip content entry requires visitors to re-subscribe").

6. **[MEDIUM] Observability / error-tracking is a completely silent dimension.** No AD, Consistency Convention, or Deferred entry says anything about how failures are surfaced: DB write errors on toggle/packing-check, push fanout failures, or admin-auth failures. For a small personal project this could reasonably be "out of scope, rely on Vercel's function logs," but that decision isn't stated anywhere — it's just absent, which the checklist flags as a finding in its own right at this altitude.
   **Fix:** Add a one-line Consistency Convention or Deferred entry: e.g., "No dedicated error-tracking service for v1; rely on Vercel's built-in function logs. Revisit if push-fanout failure rates become a problem."

7. **[LOW-MEDIUM] The two mermaid diagrams model the push path inconsistently, and the Design Paradigm diagram is technically inaccurate.** The Design Paradigm diagram draws `API -- "on unlock: web-push fanout" --> SW` — a direct edge from the server to the service worker. In reality a server can never reach a service worker directly; it always goes through the browser vendor's push service, which the Structural Seed diagram correctly models as its own `Push` node (`API -- "web-push (VAPID)" --> Push -- "delivers" --> SW`). Having the higher-level diagram omit the intermediary while the lower-level one includes it is inconsistent, and could mislead a builder about the delivery mechanism (e.g., about retry/offline semantics, which belong to the push service, not the app server).
   **Fix:** Either add the `Push` (push service) node to the Design Paradigm diagram too, or explicitly relabel the edge as "`on unlock: enqueue web-push fanout (via push service)`" so the abstraction is visibly intentional rather than an oversight.

8. **[LOW] Postgres backup / data-loss posture is unaddressed.** Nothing in AD-9, Consistency Conventions, or Deferred states whether Neon's default backup/retention is considered sufficient for the three DB-held fields (unlocked flags, push subscriptions, packing checked-state), or whether losing them (e.g., accidental branch reset) is an acceptable risk. Low stakes for this project, but silent.
   **Fix:** One line in AD-9 or Deferred: "Neon's default backup/PITR is sufficient; data loss here is low-consequence (re-toggling chapters or re-subscribing to push is cheap) and needs no dedicated backup strategy for v1."

9. **[LOW] Testing strategy is entirely unaddressed.** No AD, convention, or Deferred entry states whether there's any automated test expectation (unit, integration, e2e) for the gating logic, push fanout, or admin auth — all of which are exactly the kind of state-transition logic that's easy to get subtly wrong and hard to visually QA.
   **Fix:** Add a one-line Deferred or Consistency Convention entry, even if it's "no automated tests for v1; manual QA against the acceptance checklist in BUILD_BRIEF."

10. **[LOW] Push subscription cleanup (expired/410 subscriptions) isn't covered by AD-4 or Deferred.** AD-4 mandates fanout to "every stored subscription for that trip" on every unlock, but says nothing about what happens when a push service returns 410 Gone for a stale subscription (phone uninstalled, browser data cleared). Over a 3-day trip with 5 unlock events this is low-risk, but it's a real gap for the "reusable template" future-trips goal, where stale subscriptions could accumulate release over release.
    **Fix:** Add a sentence to AD-4: "On a 404/410 response from the push service, the subscription row is deleted." Or explicitly defer it with a note.

11. **[LOW] Structural Seed's file tree omits the Astro content-collection schema file.** `src/content/trips/` is listed as the content directory, but Astro content collections require a `src/content/config.ts` (or `.mjs`) defining the Zod schema — which is exactly where AD-7's shape would be encoded in code. Its absence is a minor completeness gap in an otherwise concrete file tree.
    **Fix:** Add `src/content/config.ts # Zod schema encoding AD-7's shape` to the tree.

12. **[LOW] Secrets rotation isn't mentioned.** Consistency Conventions states VAPID keys and the admin passcode are Vercel env vars, "never committed or hardcoded," but says nothing about rotation (e.g., if the passcode leaks to the wrong friend). Likely low priority given the scale, but worth a one-liner given AD-5 is otherwise fairly precise about the auth mechanism.
    **Fix:** One sentence: "Rotating the passcode or VAPID keys is a redeploy with a new env var value; existing sessions are invalidated by rotating the cookie-signing secret alongside it" (or explicitly defer).

## Summary of what the spine gets right

- AD-1 through AD-9 each map to a real, cited divergence risk traceable to BUILD_BRIEF/Main.dc.html/Admin.dc.html — not invented busywork.
- The Deferred section correctly avoids deferring anything that would let two builders diverge incompatibly *within v1 scope*; the items deferred (library staleness, per-person packing, real assets, hyperframes, v2 features, multi-tenant scaling) are genuinely out of v1's blast radius, with the possible exception of Finding 5 above (push-subscription/trip scoping), which touches the v1 data model even though its consequences are mostly felt at "next trip" time.
- The Stack table entries are plausible for the stated timeframe and self-flag the one real risk (`web-push` staleness) rather than hiding it.
- AD-8's reasoning (Edge runtime lacking Node `crypto` for VAPID) is a concrete, checkable technical fact, not a vague preference.
